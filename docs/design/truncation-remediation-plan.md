# 截断修复与新 baseline 重跑方案（#7 调查与计划草案）

状态：**草案，待 owner 冻结**。本文只描述调查结论、备选路线与验收方法，
不构成已批准的执行授权；小样本 GPU 与全量重跑按 #7 分阶段解锁。

## 1. 调查结论（只读核实，2026-09-20）

核实途径：仓库内代码与文档 + 对实验工作区实际脚本的只读审查（来源指纹见
[实验复盘](../colbert-experiment-review.md)；实际执行 worker 为复盘所录
finish2 worker `649300be…` 的直系变体，编码调用逐行核对）+ 一次
tokenizer-only 小样本测量。未加载模型、未使用 GPU、未扫描全量语料。

### 1.1 三层事实区分

| 层 | 事实 | 证据 |
|---|---|---|
| 原文保存 | 完整保留。`collection.tsv` 每行为 `PID\t标题 摘要`；`articles.jsonl` 按行保存 `[PID, PMID, 标题, 摘要]` 四元组；另有 `id-pmid.u64`、`source-position.u32`。仅空白规范化（`' '.join(split())`），无任何删字。空标题且空摘要的 36,617 条单独登记于 `nonsearchable.jsonl`，不静默丢弃 | prepare worker 写盘代码 |
| prepare 统计 | `truncated_tokenizer_gt255 = 19,393,571`（39,928,371 的 48.57%）。口径：**同一个 AutoTokenizer、`add_special_tokens=True`（含 [CLS]/[SEP]）、不截断**计数 `> 255`，等价于**正文 > 253 token**。按批 512 条累计，与实际编码阈值精确一致 | `prepared.json` / `prepare-checkpoint.json` + 统计代码 |
| 实际 embedding 截断 | **文档侧正文 ≤ 253**（`doc_maxlen=256`，[D]+[CLS]+[SEP] 占 3）；**查询侧正文 ≤ 29**（`query_maxlen=32`，[Q]+[CLS]+[SEP] 占 3）。截断模式 `longest_first`，从尾部切 | 实际 ColBERT 源码（复盘指纹 `cc4f3dc9`）`DocTokenizer.tensorize` / `QueryTokenizer.tensorize` |

文本顺序：`标题 + 单空格 + 摘要`。因此**截断永远先吃摘要尾部，标题总是保留**
（除非标题单独超 253）。19,393,571 的统计口径此前表述为"超过 255 token"，
实为"含特殊 token 计数 > 255"，即正文 > 253——口径与实际截断阈值一致，
可视为**被截断文档的精确计数**；它不含每篇丢失量的分布，分布见 1.2。

### 1.2 长度分布（20 万行等距抽样，tokenizer-only，CPU）

对冻结 collection 以步长 199 抽样 200,000 行，用同一模型 tokenizer
（`add_special_tokens=True`、不截断）测量正文长度（样本值，非全量）：

| 指标 | 值 |
|---|---|
| 正文 > 253（应与全量 48.57% 对账） | **48.64%**（吻合，交叉验证口径） |
| 正文 > 509（doc_maxlen=512 仍截断） | **5.38%** |
| 正文 > 761 | 0.33% |
| 分位数 p50 / p90 / p99 / p99.9 / max | 246 / 458 / 655 / 915 / 2178 |
| 未截断平均正文长度 | 234.0 token |
| 253 窗口内未被向量化覆盖的文本量占比 | **28.4%** |
| 509 窗口内未被覆盖占比 | **2.08%** |
| 向量总量比例（509 窗口 / 253 窗口） | **1.362x** |
| 253-token 分段时的平均 passage 数/篇 | 1.546 |

限制：等距抽样单次执行、无重复实验；样本隐含平均向量数（~170/条）与既有
预算的 `vectors_per_record_assumed=156.44`（500k 前身语料假设值）及按实际
索引体量反推值（~161/条）存在 ±8% 级差异——**比例（1.36x）比绝对值可靠**，
绝对预算以小样本实测校准为准。

## 2. 修复路线对比

### 路线 A：更长窗口（doc_maxlen 256 → 512）

- 依据：模型为 bert-base 结构，`max_position_embeddings=512`，窗口上限即 512，
  **无需改模型或 ColBERT 源码**（仓库入口已支持 `--doc-maxlen` 4..512）。
- 效果：未覆盖文本量 28.4% → **2.08%**（约 13.6 倍改善）；5.38% 的文档仍有尾部丢失。
- 成本（比例法估算，待小样本校准）：向量总量 ×1.362 → 索引约
  215.67 GiB × 1.362 ≈ **294 GiB**；构建时长同比例（×1.36，基准 142 passages/s
  双 rank 顺序构建）；kmeans/编码内存按向量数同比例上升，现有 ~88 GiB 内存约束
  需实测确认余量。
- 合同影响：**零变更**。PID/PMID 映射、Searcher 语义、同版本文本读取
  （`articles.jsonl` 模式）全部沿用。

### 路线 B：长文本分段（passages）

- 做法：正文按 253-token passage 切分（可选 50-token 重叠），每 passage 独立编码。
- 效果：**覆盖 100% 文本**（含 >512 的 0.33%+ 长文）。
- 成本：passage 总量 ≈ 39.93M × 1.546 ≈ **61.7M**；向量总量 ≈ ×1.40（无重叠）
  至 ×1.49（50 重叠），与 A 相当；查询侧候选 fan-out ×1.55，延迟上升。
- 合同影响（需 owner 决策，不静默选择）：passage→(PID, PMID) 映射新增维度；
  单篇去重/聚合语义（如每 PMID 取最高分 passage 的 MaxP 式聚合）属于**排名合同
  变更**；#5 冻结的 corpus/shard/text 版本合同需扩展 passage 维度；返回同版本
  完整文本仍从文本层取（不拼 passage）。

### 查询侧（两路线通用，且**不需要重建索引**）

查询在检索时编码，不入索引。`query_maxlen` 可在 Searcher 配置侧调整并独立评估；
实际 ColBERT 源码含 `full_length_search` 单查询全长度路径。查询正文上限现为
29 token，标题型查询基本覆盖，长自然语言查询被切。**建议与索引修复解耦**，
在小样本验收中单独评估提升到 64 的影响（模型按 32 训练，行为变化需实测）。

## 3. 推荐方案

**推荐 A（doc_maxlen=512 重跑新 baseline）+ 查询侧独立评估**：

1. 以 2.08% 残余尾部丢失换取零合同变更与最低实现风险；1.36x 成本可接受；
2. B 的全量覆盖优势需以排名/存储合同变更为代价，且其增量收益主要落在 5.38%
   文档的尾部——先量化这 5.38% 是否影响检索质量，再决定是否升级到 B；
3. 若小样本验收显示尾部丢失仍显著影响召回，A 的目录结构与映射设计预留
   passage 扩展位（PID 编号不变，passage 表可后加）。

**最小备选**：A' = 仅对受影响最重的长文子集补分段（混合策略），实现与合同
复杂度介于两者之间，仅当 A 验收失败且 B 预算超限时考虑。

## 4. 小样本验收（go/no-go 前置，需 owner 批准 GPU 资源）

规模建议两档：50k（快速）与 500k（对齐既有容量实验规模），均写入**新目录**，
输入复用冻结的 verified inputs（哈希清单不变）。验收项：

1. **尾部信息用例**：抽取正文 > 400 token 的文档 ≥ 100 篇，取其摘要 253 token
   之后的关键词构造查询；新索引应命中对应文档，旧索引预期不命中。记录命中率。
2. **标题自检索**：30 查询 30/30 不得回归。
3. **行为对照**：与旧索引 top-10 重合度记录变化幅度（描述性，不作质量结论）。
4. **资源实测**：吞吐（passages/s）、内存峰值、单片磁盘占用 → 校准全量预算
   （修正 1.2 节 ±8% 不确定度）。
5. **查询侧**：query_maxlen 32 vs 64 对照（同一索引），记录延迟与排序变化。

**go**：尾部用例显著命中、自检索无回归、内存峰值 < 约束并留余量、磁盘符合
新预算 → 进入全量。**no-go**：内存超限（先降 index_bsize 或缩方案）、质量回归
（评估 B）、预算无法满足（上报 owner 重新决策）。

## 5. 全量重跑步骤与旧库保护

1. 新目录族与现有 10 片**物理分离**；现有索引与全部输入产物只读保留
   （首版交付继续使用旧库，直到切换另行验收决定）。
2. 流程沿用 verify → build → coalesce → query 与 supervisor 监督；
   worker 仅改 `doc_maxlen` 一个值，其余参数（dim128/nbits2/query32/
   index_bsize64/kmeans_niters4）不动。
3. supervisor 磁盘线不沿用写死的 700 GiB：按实测单片占用 × 安全系数重估；
   内存线按小样本实测重设。
4. 预计构建时长 = 既有总时长 × 1.36（142 passages/s 基准比例法）；GPU 选择
   沿用构建前空闲检查。
5. 完成后按 #7 关闭条件执行覆盖/映射/查询验收；服务切换不在本方案内。

## 6. 成本估算方法论

- 向量数 = Σ min(正文, 窗口−3) + 3×记录数（分段则为 Σ(每 passage 正文+3)）；
- 索引各成分（kmeans 训练内存、IVF、coalesce、压缩码）对向量总量近似线性，
  比例系数取自既有 budget 模型（来源型估算，非实测峰值）；
- 抽样比例法给出相对倍数（本调查 1.362x），绝对值以小样本实测校准；
- 未知项明确标注：全量内存峰值、512 窗口下的实际吞吐、>509 文档的检索质量
  影响——均由第 4 节验收补齐。
