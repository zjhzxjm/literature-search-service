## 目标与边界

从已下载的 PubMed baseline 和 updatefiles 建立可持续维护的文献检索服务：年度重建，年内按来源顺序应用新增、修订、删除；支持 ColBERT 与 Elasticsearch，配置 ColBERT 时优先使用，运行失败不静默回退。

首版沿用 SciClaims 检索语义，不做混合召回、复杂质量评测、全文下载、声明核验、扩展筛选或新的同步下载程序。服务采用已确认的 Python/FastAPI、独立导入 CLI、SQLite 进度账本、单导入写者；每日批次允许逐步可见，但必须如实报告完整进度和失败状态。

完成服务需要真实后端读写、恢复、API、年度切换和运维验证。解析模块与接口替身测试完成不等于服务交付。

## 数据流及所有权

```text
已下载的年度 baseline / updatefiles（外部输入）
  → 共用 PubMed 解析与有序变更事件
  → 文献保存与重放边界（R0 决定）
  → 所选后端的索引、文献读取和版本绑定
  → 检索 API

SQLite 导入账本记录批次和成功进度，不冒充文献正文存储。
```

原始文件由现有同步流程提供，本服务不改写。是否保存标准化中间文件、当前文献放在哪里、ColBERT 内部 ID 映射如何持久化尚未确认。不同后端必须绑定同一批次所对应的文本与标识；不依赖接口调用者自行保证版本正确作为最终实现。

## R0：先确认解析结果保存在哪里

已确认的第一部分：ColBERT 搜索返回已发布索引版本的匹配文本，新增、修订和删除在对应更新发布后生效，并区分来源处理与搜索发布进度。具体行为见[设计中的更新可见性与文本一致性约定](design/pubmed-search-v1.md#colbert-更新可见性与文本一致性r0-部分已确认)。这项确认不代表 R0 整体完成，也不确定存储或发布实现。

问题：目前解析结果只在内存中逐条产生。两个后端都需要可靠的文献内容、身份和恢复边界，继续实现导入前必须确定保存方式。

需要逐项讨论：

1. 是否保存标准化 JSONL 中间文件。保存会增加空间及版本清理成本，但可以避免重复 XML 解析并复用输入；直接解析到后端减少磁盘副本，但重建或重试可能重新解析源文件。
2. 当前文献按 PMID 读取的位置。JSONL 批次本身不等于支持随机查询、修订和删除的当前文献库；不能只选择文件格式就视为解决了文献读取。
3. ColBERT 的内部 ID、PMID、实际编码文本与索引版本如何持久化绑定。已确认不得把新修订文本返回为旧向量命中的证据；绑定格式和验证机制尚未确定。
4. 原始数据与中间产物的保留期、删除权限和重放条件。原始 XML、标准化事件、当前文献和索引各自的作用必须唯一明确。

先比较“直接导入”和“标准化文件复用”两个适量方案；不预先引入多来源主数据库或双后端同时写入。接受条件是用户确认保存位置的逻辑职责、修订/删除语义、恢复与保留规则；确认后更新设计并定义合成输入/预期输出。

### ColBERT 后续执行安排（提案，存储选择待确认）

下面按交付顺序衔接文本读取、每日更新及完整语料的查询成本，不把独立实验直接升级为正式服务验收。文本存储候选及其取舍见[设计文档](design/pubmed-search-v1.md)。暂定目标沿用此前容量验证的 2 并发 P95 不超过 1 秒；正式 API 指标需包含取文本与网络开销，仍需确认。

| 顺序及归属 | 可交付结果 | 验收与停止条件 |
|---|---|---|
| 前置：R0/R5，构建与查询资源联合评估 | 核实可分配离线节点、单进程内存、共享与本地存储、环境兼容性，并对照正式 API 主机预算比较布局 | 区分编码批次、索引 chunk、搜索分片和文本文件；先评估单一逻辑索引、少量索引及分批构建后统一查询，不以实验布局固定架构。跨机器交接需验证官方阶段能力与恢复约束。 |
| A：R0/R1，文本与最小真实查询闭环 | 确认文本存储合同；把参数化的建库、映射、合并、清单及验证代码整理入库；通过项目适配器完成命中后批量读文本 | 优先复用已有索引，不新增大规模 GPU 建库。核对实际 PMID、内容版本与返回文本；覆盖 k=1/3/10、缺失或错误映射、错版本、无命中、并发和重新加载。分别计时检索、取文本、序列化。先解决项目 Python 要求与实验环境不一致的问题。 |
| B：R2，可靠每日更新闭环 | 在隔离小数据上完成新增、完整替换、删除、重放、发布与恢复；识别旧版本的失效命中 | 先用合成事件做确定性故障测试，再在声明文件范围的真实 updatefiles 上测变更量和成本。不直接复用此前未通过验收的更新器。重复执行不重复生效；失败不越过进度；旧文本与新向量不能混用；源文件变化显式失败。 |
| C：R5 前置，完整语料成本决策 | 冻结实际源文件边界，给出当前有效记录统计、候选索引布局、内存/存储预算、建库时间范围和每日维护成本 | 先得到输入和更新成本证据，再决定是否需要一次更大单索引的阶段验证，避免反复扩大总样本。将分片数量、常驻结构、模型、活跃文件页、文本读取、并发和新旧版本切换峰值分别计入；同样计入原索引、mmap 合并副本、暂存及回退空间。小样本及假设数量的外推不等于全量通过。 |
| D：R3/R4/R5，API 与全量验收 | 在确定的 API 主机接通实际调用方，完成完整语料的查询、每日更新和发布切换验收 | 先验收隔离小数据 HTTP 闭环及认证/网络范围，再执行单独确认的全量构建和部署。测完整请求 P95、启动、持续并发、共享存储读取、索引切换时双版本内存，以及查询和更新同时进行的影响；不能只引用缓存已热的内核检索延迟。 |

在索引布局联合评估后，R2 再比较更新实现成本，例如：替换受影响的分片，或构建独立变更段并维护发布版本中的有效记录选择。前者读侧较简单，但分散修订可能导致大量重建；后者减少即时重建，但引入查询合并、过期记录过滤及周期合并的成本。先测真实更新分布和小数据恢复行为，再选择，不同时实现两套正式机制。若采用变更段，必须在最终 top-k 确定前排除旧修订和删除记录，并验证过滤造成候选不足时的处理；不能先取 top-k 再简单删掉失效结果就宣称语义正确。

故障注入至少覆盖：变更读取中断、编码中断、产物写完但未登记、发布前中断、发布完成但账本未确认、查询期间切换、重放同一文件、同名文件校验值变化、同 PMID 多次修订、删除后再新增，以及连续批次失败。发布和来源检查点都要可核验，不能只依赖进程退出码。每日完成窗口与周期合并预算以实际变更量测算；不能用“每天启动一次定时任务”代替可靠每日更新验收。

脚本入库是正式交付要求：业务逻辑进入包内建库模块，CLI 负责参数和启动；路径、设备、批次和资源上限配置化；保留模型/代码版本与产物校验信息。真实语料、索引、模型、内部路径与日志留在仓库外。具体模块拆分随首个实现增量落地，不先生成空骨架；入库整理、测试通过、提交和推送分别记录。

当前下一步是前置的构建与查询资源联合评估，完成后再讨论 A 的存储合同及验收输入；本表是执行安排提案，不表示 B–D 已开始或全量运行已授权。

## R1：已有代码收尾

- 对照实际 XML 小样本验证核心字段，保留缺失摘要、嵌套文本、删除与损坏输入的测试；不上传真实文献作为公开测试夹具。
- 在隔离 ES 测试索引上对照原 SciClaims 查询；比较 ID、顺序、原生排名、原始分数及命中文本。原生并列结果不添加自定义排序。
- 接收 ColBERT 独立验证的代码/模型版本、Python/PyTorch/CUDA 环境、索引参数和 ID 映射证据，核对本包 Python 要求；再通过本项目适配器完成实际查询和内容读取。
- 补齐索引与映射不匹配、缺失映射、加载失败不回退的验收；不得只测试一个内存字典就宣称持久化映射已完成。

接受条件：两个后端分别留下真实调用证据，现有解析和请求测试通过；跳过测试仍是未完成。不要把原生 ES 零起始 rank 与 ColBERT 一起始 rank 统一成一个未说明的行为。此增量不建设全量库。

## R2：账本与增量维护

先共用文件身份、校验值、来源次序和检查点，再实现单个后端的事件应用。ES 使用逐项检查的批量写入；ColBERT 采用验证后确认的新增、修订、删除方式，不套用 ES 的覆盖机制。

接受条件：新增、修订移除旧字段、未知 PMID 删除、重复执行、同名文件内容变化、部分失败、写入后账本提交前崩溃、恢复后继续处理均有可重跑测试。未恢复失败文件不能越过推进；索引与返回文本一致。若 ColBERT 无法以可接受成本正确应用每日更新，回到该项讨论，不能静默降为只支持年度重建。

## R3：查询服务

通过共用接口提供搜索、按 PMID 读取和状态查询；标明后端、数据版本、最近完整文件及当前执行状态。返回命中文本的版本应与本次检索一致。完整定义无命中、已删除、批次过期、后端不可用和非法参数的响应。

接受条件：用已验收小数据索引完成端到端 HTTP 测试；模型不在每个请求中重复加载；选用 ES 时不要求 ColBERT 依赖。明确认证及网络访问范围后才部署。

## R4：年度生命周期

新年度 baseline 在独立批次构建并追上明确更新边界，验证后切换。ES 可采用别名；ColBERT 的索引、映射、文本及服务加载状态须作为同一批次切换，具体机制在 R1/R2 证据上确定。

接受条件：小数据演练切换前、切换中、切换后的查询和中断恢复；旧批次保留与回退明确；不会向用户暴露半成品年度库。清理只限明确授权的过期派生产物。

## R5：运行与发布

只做必要的容量与吞吐测量，不扩展复杂检索质量评测。先记录样本上限、代表性局限、时间/空间预算和通过阈值，再测实际索引及更新成本；全量容量必须计入文本、映射、年度双库和临时空间。

接受条件：存储布局及峰值余量有依据；全量导入和部署范围得到确认；服务健康、实际查询、每日更新和恢复检查通过。补齐安装、配置、恢复、年度切换手册；选择项目许可证，保留第三方声明和数据来源/使用边界。模型、语料、运行日志、机器路径和密钥不进入公开仓库。
